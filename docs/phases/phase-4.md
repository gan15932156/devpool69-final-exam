# Phase 4 — การจองของฉัน · แก้ไข · ยกเลิก

**ผลลัพธ์:** หน้า `/bookings` แท็บ กำลังจะถึง / ที่ผ่านมา / ยกเลิกแล้ว · แก้ไขผ่าน dialog (มือถือเป็น bottom sheet) · ยกเลิกมีขั้นยืนยัน · เลยเวลา → ปุ่ม disabled

## API

| Method | Path | หมายเหตุ |
|---|---|---|
| GET | `/me/bookings` | `{ upcoming, past, cancelled }` |
| PUT | `/bookings/:id` | `booking.Update` → ตรวจกติกาเดียวกับจองใหม่ + `excludeID` |
| POST | `/bookings/:id/cancel` | ได้เมื่อ `now ≤ startAt − lead` (`booking.CanModify`) |

## ไฟล์หลัก

`api/internal/booking/service.go` (Update, Cancel, loadOwnBooking, CanModify) · `api/internal/handlers/my_bookings.go` · `web/app/(main)/bookings/MyBookingsView.tsx` · `web/components/booking/BookingStub.tsx`, `EditBookingDialog.tsx`

## การตัดสินใจ และเหตุผล

| เรื่อง | เลือก | ทำไม | ทางอื่นที่ไม่เลือก |
|---|---|---|---|
| แก้ไขไม่นับที่เดิมซ้ำ | `CheckSeats(..., excludeID = id)` → query ใส่ `id <> ?` | ร้าน 10 ที่ · A 7 · B 3 → A แก้เป็น 8 ต้องคิด 3 + 8 = 11 ✕ ไม่ใช่ 3 + 7 + 8 · ใช้ฟังก์ชันเดียวกับจองใหม่ → กติกาไม่มีทางเพี้ยนกัน | เขียน logic แก้ไขแยก |
| แก้ไข = update แถวเดิม | ไม่ใช่ ยกเลิกแล้วสร้างใหม่ | id เดิม ประวัติไม่กระจัดกระจาย · ทำใน transaction เดียวกับการตรวจ | cancel + create: ถ้าพังกลางทาง ที่เดิมหายแต่ที่ใหม่ไม่ได้ |
| lock ตอนแก้/ยกเลิก | ล็อกแถวร้านเหมือนตอนจอง แล้วอ่านการจองซ้ำหลังได้ lock | ทุกการเปลี่ยนแปลงของร้านเดียวกันต่อคิวที่จุดเดียว · กันกรณีแก้กับยกเลิกพร้อมกัน | ล็อกแค่แถวการจอง: การแก้ไขที่เพิ่มคนยังชนกับการจองใหม่ของคนอื่นได้ |
| เลยเวลายกเลิกแล้วแก้ไขได้ไหม | **ไม่ได้** (409 `CANCEL_WINDOW_PASSED`) | ตกลงไว้ใน WALKTHROUGH · กันการ "ลดคนเหลือ 1" แทนการยกเลิกตอนใกล้เวลา | ดีไซน์ยังให้แก้ได้ — เปลี่ยนตามที่ตกลง |
| สิทธิ์ | การจองของคนอื่น → 403 | สอดคล้องกับร้าน (403 เหมือนกัน) | 404: ซ่อนว่ามี id นี้ แต่ต้องอธิบายสองแบบ |
| ยกเลิกซ้ำ / แก้ที่ยกเลิกแล้ว | 409 `BOOKING_CANCELLED` | ข้อมูลถูกรูปแบบแต่ขัดกับสถานะ | — |
| ยกเลิก = เปลี่ยน status | ไม่ลบแถว + เก็บ `cancelled_at` | เจ้าของร้านยังเห็นประวัติ · ที่นั่งคืนทันทีเพราะนับเฉพาะ `confirmed` | ลบแถว: ประวัติหาย |
| `canCancel` | คิดที่ Go ส่งมาใน JSON ด้วย `booking.CanModify()` ตัวเดียวกับที่ `Update`/`Cancel` ใช้ตัดสิน | หน้าเว็บไม่ต้องรู้กติกาเวลา · ปุ่ม disabled ตรงกับที่ Go จะตอบเสมอ เพราะกติกาอยู่ฟังก์ชันเดียว | เขียนเงื่อนไขซ้ำใน DTO: แก้กติกาแล้วลืมแก้อีกที่ |
| แบ่งแท็บ | upcoming = ยืนยัน + ยังไม่จบ · past = ยืนยัน + จบแล้ว · cancelled = ยกเลิก | ตามดีไซน์ (3 แท็บ) | — |
| ข้อมูลร้าน/เคยรีวิว | ดึงรวมครั้งเดียว (`Preload("Restaurant")` + รีวิวของผู้ใช้ 1 query) | ไม่ query ทีละการจอง (N+1) · ไม่ส่งรูปร้านมาด้วยเพราะการ์ดการจองไม่ได้แสดงรูป | — |
| dialog | `<dialog>` ของเบราว์เซอร์ + `showModal()` | Esc ปิดได้ · โฟกัสวนใน dialog · กลับไปปุ่มเดิมเมื่อปิด — ได้ฟรีไม่ต้องเขียนเอง | lib modal: เพิ่ม dependency |
| มือถือ | dialog เดียวกัน จัด CSS ให้ชิดล่างเต็มกว้าง (bottom sheet) | ไม่ต้องมีสอง component | — |
| จุดที่นั่ง | availability + `excludeBookingId` → Go ส่งตัวเลขที่ไม่รวมที่เดิมมาให้ | ตัวเลขใน dialog ตรงกับที่ Go จะใช้ตัดสิน | ให้หน้าเว็บลบเอง |
| ยกเลิก | กดแล้วมีแถบชมพูยืนยัน inline | ตามดีไซน์ · กันกดพลาด | `confirm()`: หน้าตาไม่ตรงดีไซน์ |
| หลังจอง/แก้/ยกเลิก | `invalidateBookingQueries()` ใน `lib/booking.ts` → invalidate `["my-bookings"]` + `["availability"]` | การ์ดย้ายแท็บ/อัปเดตทันทีโดยไม่ reload · 3 จุดที่เปลี่ยนการจองใช้ฟังก์ชันเดียวกัน | เขียน invalidate เองทุกจุด: เพิ่ม query ใหม่แล้วลืมบางจุด |

## ทดสอบแล้ว

- A 7→8 → 409 `used 3` · A 7→5 → 200 · A 5→7 → 200 (ที่เดิมไม่ถูกนับซ้ำ)
- B แก้การจองของ A → 403 · ยกเลิกซ้ำ → 409 · แก้การจองที่ยกเลิก → 409
- หลังยกเลิก availability ช่องนั้นลดลงทันที
- การจองที่เหลือ 10 นาที (ร้านให้ยกเลิกล่วงหน้า 30 นาที) → แก้/ยกเลิกได้ 409 · ในหน้าเว็บปุ่ม disabled + ข้อความชาด
- เบราว์เซอร์: dialog เพิ่มเป็น 8 → "ที่นั่งไม่พอ — คนอื่น 3 + คุณ 8 = 11" + ปุ่มบันทึก disabled · ลดเป็น 5 → บันทึกได้ DB เป็น 5 · ยกเลิกแล้วการ์ดย้ายไปแท็บยกเลิก
