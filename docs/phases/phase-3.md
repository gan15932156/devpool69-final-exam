# Phase 3 — การจอง (แกนหลัก · ใช้อธิบายในวิดีโอ)

**ผลลัพธ์:** ใบจองโต๊ะในหน้าร้าน · Go ตรวจกติกาทุกข้อ · สองคนจองที่นั่งสุดท้ายพร้อมกัน → ได้คนเดียว

## ไฟล์หลัก

| ไฟล์ | หน้าที่ |
|---|---|
| `api/internal/booking/time.go` | แปลง "วันที่ + HH:MM" เป็นเวลาจริง · ร้านข้ามเที่ยงคืน |
| `api/internal/booking/validate.go` | ตรวจกติกาที่ไม่ต้องดูการจองคนอื่น |
| `api/internal/booking/service.go` | **lock + ตรวจที่นั่งทีละช่อง + สร้าง/แก้/ยกเลิก** |
| `api/internal/handlers/bookings.go` | HTTP → เรียก `booking.*` · แปลงเป็น JSON |

## กติกาทำงานยังไง

**① แปลงเป็นเวลาจริง (เวลาไทย)** — `time.go`
```
ร้าน 18:00–02:00 รอบวันที่ 25:
  ช่วงเปิด  = 25 18:00 ถึง 26 02:00          (ปิด ≤ เปิด → ปิดของวันถัดไป)
  "01:00"   = 26 01:00                       (อยู่ช่วง 00:00–เวลาปิด → วันถัดไป)
  "17:30"   = 25 17:30 → นอกเวลา              (ไม่ใช่ช่วงหลังเที่ยงคืน → วันเดียวกัน)
```

**② ตรวจตามลำดับ** — `validate.go` (เจอข้อแรกที่ผิดก็หยุด แต่ละข้อ code ต่างกัน)

| ลำดับ | ตรวจ | code |
|---|---|---|
| 1 | รูปแบบวันที่/เวลา | `VALIDATION` |
| 2 | ลงที่ :00 / :30 | `INVALID_SLOT` |
| 3 | สิ้นสุด > เริ่ม | `INVALID_RANGE` |
| 4 | อยู่ในช่วงเปิด | `OUTSIDE_HOURS` |
| 5 | เวลาเริ่มยังไม่ผ่าน | `IN_PAST` |
| 6 | จำนวนคน ≥ 1 | `VALIDATION` |
| 7 | ที่นั่งพอทุกช่อง | `SEATS_EXCEEDED` (409) |

**③ ตรวจที่นั่งใน transaction** — `service.go`
```go
db.Transaction(func(tx *gorm.DB) error {
    r := lockRestaurant(tx, id)            // SELECT ... FOR UPDATE → คนที่มาทีหลังรอตรงนี้
    slot := Validate(r, input, now)
    CheckSeats(tx, r, slot, party, 0)      // ดึงการจองที่ซ้อน → วนทีละช่อง 30 นาที
    tx.Create(&booking)
})
```

## การตัดสินใจ และเหตุผล

| เรื่อง | เลือก | ทำไม | ทางอื่นที่ไม่เลือก |
|---|---|---|---|
| กันจองพร้อมกัน | **transaction + `SELECT … FOR UPDATE` ที่แถวร้าน** | ทุกการเปลี่ยนแปลงการจองของร้านเดียวกันต่อคิวทีละรายการ → คนที่สองเห็นการจองของคนแรกแล้วแน่นอน · ร้านอื่นไม่ต้องรอ (ล็อกแค่แถวเดียว) | **unique constraint**: ใช้กับ "ที่นั่ง 1 ที่ = 1 แถว" ได้ แต่ร้านนี้นับที่นั่งรวม ไม่มีอะไรให้ unique · **SERIALIZABLE**: ได้เหมือนกันแต่ต้องเขียน retry เมื่อ conflict · **ล็อกทั้งตาราง bookings**: ร้านอื่นต้องรอด้วย · **เช็กแล้วค่อย insert โดยไม่ล็อก**: สองคนเห็นที่ว่างชุดเดียวกัน → จองเกิน |
| ทำไมล็อกแถว "ร้าน" ไม่ใช่แถวการจอง | ช่วงที่ขออาจยังไม่มีแถวการจองให้ล็อกเลย | ล็อกได้แค่แถวที่มีอยู่ · แถวร้านมีเสมอและเป็นจุดร่วมของทุกการจองของร้านนั้น | — |
| ต้องใช้ `tx` ทุกคำสั่ง | ใน `Transaction` ห้ามใช้ `db` ข้างนอก | query ที่ใช้ `db` จะอยู่นอก transaction → ไม่ถูกล็อกคุม | — |
| นับที่นั่ง | **วนทีละช่อง 30 นาที** | ต้องรู้ว่า "ณ เวลาใดเวลาหนึ่ง" มีคนนั่งพร้อมกันกี่คน · การจอง 12:00–12:30 (7 คน) กับ 13:00–13:30 (7 คน) ไม่ได้ซ้อนกันเอง ถ้ารวมทั้งช่วง 12:00–13:30 จะได้ 14 ซึ่งผิด (ทดสอบแล้ว: จองผ่าน) | รวม party ของทุกการจองที่ซ้อนกับช่วงที่ขอ: นับเกินจริง |
| ทำไมช่องละ 30 นาทีพอ | เวลาทุกอย่างบังคับลง :00/:30 | จำนวนคนเปลี่ยนได้เฉพาะที่ขอบ 30 นาที → ดูทีละ 30 นาทีได้ครบทุกจังหวะ | ดูทีละนาที: ผลเท่ากันแต่ช้ากว่า 30 เท่า |
| บังคับ :00/:30 | ตรวจที่ Go (ไม่ใช่แค่ UI) | ตกลงไว้ใน WALKTHROUGH · ทำให้การตรวจทีละช่องถูกต้อง | — |
| error ที่นั่งเกิน | 409 + `details: {slotStart, slotEnd, used, party, seats}` | หน้าเว็บเขียนข้อความเองได้ (`seatsExceededText` ใน `web/lib/booking.ts`) · 409 = ข้อมูลถูกรูปแบบแต่ขัดกับสถานะปัจจุบัน | 400: ดูเหมือนผู้ใช้กรอกผิด |
| response | ส่ง `serviceDate`, `start`, `end` เป็นสตริงเวลาไทย | หน้าเว็บไม่ต้องแปลง timezone เอง | ส่งแค่ ISO: ทุกหน้าต้องแปลงเอง |
| `ServiceDate` ลงคอลัมน์ `date` | `DateOnly()` = เที่ยงคืน **UTC** | เที่ยงคืนเวลาไทย = 17:00 UTC ของวันก่อน → Postgres ตัดเป็น "วันก่อนหน้า" (บั๊กที่เจอบ่อย) | — |
| `now` | ส่งเข้า function เป็นพารามิเตอร์ (`h.Now`) | ทดสอบ/จำลองเวลาได้ · ทั้ง request ใช้เวลาเดียวกัน | เรียก `time.Now()` กระจายหลายที่ |
| Availability | ใช้ `overlapping` + `usedIn` ตัวเดียวกับ `CheckSeats` | ตัวเลขในกราฟตรงกับที่ Go ใช้ตัดสินเสมอ | เขียน query แยก: เสี่ยงคิดไม่ตรงกัน |
| Availability ต้อง login ไหม | ไม่ต้อง | ดูหน้าร้านได้ก่อน login · `excludeBookingId` ใช้ได้เฉพาะการจองของตัวเอง | — |
| หน้าเว็บคำนวณซ้ำ | `lib/booking.ts` ตรรกะเดียวกับ Go + `renderVals()` ในดีไซน์ | ผู้ใช้เห็นผลทันทีก่อนกด · **แต่ถ้า Go ตอบ error ต้องแสดงตาม Go เสมอ** (เช่น มีคนจองตัดหน้า) แล้วโหลดกราฟใหม่ · ข้อความ error ใช้ `bookingErrorText()` ตัวเดียวทั้งใบจองและ dialog แก้ไข | ไม่คำนวณ: ผู้ใช้ต้องกดแล้วรอผิดเอง |
| เลือกเวลา | `<select>` เริ่ม/สิ้นสุด ทีละ 30 นาที · ร้านข้ามคืนรายการต่อไปถึงหลัง 00:00 | เลือกค่าที่ผิดไม่ได้ตั้งแต่แรก · ช่องที่ผ่านไปแล้ว disabled | input type=time |
| วันที่ | ปุ่มทรงซุ้ม 5 วัน (วันนี้ + 4) | ตามดีไซน์ · backend ไม่จำกัดว่าจองล่วงหน้าได้ไกลแค่ไหน | — |
| แปลงวันที่จาก request | `booking.ParseDateParam()` + `booking.DateLayout` | ทุก endpoint ที่รับ `date` ตอบ error รูปแบบเดียวกัน · รูปแบบ `2006-01-02` อยู่ที่เดียว | เขียน parse + ข้อความ error ในแต่ละ handler |
| ชื่อวัน/เดือนภาษาไทย | array กำหนดเอง (`ศ.`, `ก.ย.`) | `toLocaleDateString` แต่ละเบราว์เซอร์ย่อไม่เหมือนกัน (Edge ให้ "ศุกร์") | — |
| กราฟที่นั่ง | `div` ธรรมดา | 1 แท่ง = 1 ช่อง ไม่ต้องมีแกน/tooltip ซับซ้อน · ไม่ต้องเพิ่ม lib | Recharts/Chart.js: หนักเกินจำเป็น |
| screen reader | ผลตรวจอยู่ใน `aria-live="polite"` · ✓/✕ มีข้อความ "ผ่าน/ยังไม่ผ่าน" | HANDOFF §8: สถานะไม่สื่อด้วยสีอย่างเดียว | — |
| เจ้าของจองร้านตัวเอง | อนุญาต | โจทย์ห้ามแค่รีวิวร้านตัวเอง | — |

## คำถามที่กรรมการอาจถาม

- **ถ้าสองคนกดพร้อมกันจะเกิดอะไร?** — ทั้งคู่เข้า transaction แต่คนที่สองติดอยู่ที่ `FOR UPDATE` จนคนแรก commit แล้วจึงเห็นการจองของคนแรก → ที่นั่งไม่พอ → 409 · เดโมด้วย `race.sh` ได้
- **ทำไมไม่ใช้ SERIALIZABLE?** — ได้ผลเหมือนกัน แต่ Postgres จะยกเลิก transaction ที่ชนกันแล้วเราต้องเขียนวนลองใหม่เอง · FOR UPDATE ให้รอคิวแทน โค้ดตรงไปตรงมากว่า
- **ถ้าร้านมีการจองเยอะมาก ล็อกแถวร้านจะช้าไหม?** — การจองของร้านเดียวกันต่อคิวกัน แต่ใช้เวลาแค่ไม่กี่มิลลิวินาที · ร้านอื่นไม่กระทบเลย
- **ทำไมเก็บเวลาเป็น timestamptz?** — ร้านข้ามเที่ยงคืนทำให้ "01:00" อาจเป็นวันถัดไป · เก็บเป็นจุดเวลาจริงแล้วเทียบช่วงซ้อนด้วย `start < otherEnd AND end > otherStart` ได้ตรง ๆ ไม่มีกรณีพิเศษ
