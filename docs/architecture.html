3ชั้นของ Go API

คำขอไหลจากบนลงล่าง แพ็กเกจ booking ไม่รู้จัก HTTP เลย มันรับ *gorm.DB กับเวลา now เข้ามาเป็นพารามิเตอร์ ตัว seed จึงเรียกใช้ฟังก์ชันชุดเดียวกับ API และทดสอบด้วยเวลาที่กำหนดเองได้

  1. cmd/api/main.goโหลด config → ต่อ DB → reset/migrate/seed → เตรียมกุญแจ JWT → สร้าง Fiber พร้อม recover และ error handler กลาง
  2. handlers/routes.goผูก URL กับ middleware ตามลำดับ เช่น auth → limit.write → handler
  3. middleware/auth.goRequireAuth (ไม่มี token ตอบ 401) · OptionalAuth (ไม่บังคับ login แต่ถ้า login อยู่จะรู้ว่าเป็นใคร เช่นหน้าร้านต้องรู้ว่าคนดูเป็นเจ้าของไหม)
  4. handlers/limits.gorate limit แยกตามกลุ่ม route และค่าจำกัดที่กันการใช้งานในทางผิด
  5. handlers/*.goอ่าน JSON · ตรวจสิทธิ์ (เป็นเจ้าของร้านไหม) · แปลงผลลัพธ์เป็น response
  6. booking/validate.go กติกา 7 ข้อ · time.go เวลาไทยและร้านที่เปิดข้ามเที่ยงคืน · service.go ล็อกแถวร้านและนับที่นั่ง
  7. apperr/ทุก error ตอบหน้าตาเดียวกัน {"error":{"code","message","details"}} หน้าเว็บจึงแยกได้จาก code ว่าผิดเพราะอะไร
  8. models/ · database/GORM struct พร้อม constraint (CHECK, UNIQUE, ON DELETE CASCADE) และ AutoMigrate

4หัวใจของระบบ: การจอง

การจอง แก้ไข และยกเลิกทำงานใน transaction เดียวกันเสมอ ขั้นแรกคือ SELECT … FROM restaurants WHERE id = ? FOR UPDATE ดังนั้นคำขอที่แตะร้านเดียวกันจะต้องเข้าคิวรอกัน ส่วนร้านอื่นทำงานคู่ขนานได้ตามปกติ

สองคนกดจองที่นั่งสุดท้ายพร้อมกัน

นับที่นั่งทีละช่อง 30 นาที

เราไม่ได้รวมจำนวนคนของทุกการจองที่ซ้อนกับช่วงที่ขอ เพราะการจองสองรายการที่อยู่คนละช่วงกันไม่ได้นั่งพร้อมกันจริง CheckSeats จึงไล่ดูทีละช่อง 30 นาที และทุกช่องต้องผ่านเงื่อนไข ที่จองแล้ว + คนที่ขอ ≤ ที่นั่ง

รวมทั้งช่วงแบบตรง ๆ7 + 7 + 3 = 17 > 10 ✕ปฏิเสธคำขอที่จริง ๆ ยังมีที่นั่งให้
ดูทีละช่อง 30 นาที (ที่ใช้จริง)7 + 3 = 10 ≤ 10 ✓ ทั้งสองช่องตรงกับจำนวนคนที่นั่งพร้อมกันจริง

ร้านที่เปิดข้ามเที่ยงคืน

เวลาเปิดและปิดเก็บเป็นนาทีนับจากเที่ยงคืน ถ้า close ≤ open แปลว่าร้านปิดหลังเที่ยงคืน เวลาที่ลูกค้าเลือกในรอบวันที่ 25 ซึ่งตกอยู่หลังเที่ยงคืน จะถูก Resolve() ให้เป็นเวลาของวันที่ 26

กติกาที่ตรวจก่อนนับที่นั่ง (Validate)

  1. วันที่และเวลาอยู่ในรูปแบบ YYYY-MM-DD และ HH:MM
  2. เวลาลงที่ :00 หรือ :30 เท่านั้น (INVALID_SLOT)
  3. เวลาสิ้นสุดอยู่หลังเวลาเริ่ม (INVALID_RANGE)
  4. อยู่ในเวลาเปิดของรอบนั้น (OUTSIDE_HOURS)
  5. เวลาเริ่มยังไม่ผ่านไป (IN_PAST)
  6. ไม่เกิน 60 วันข้างหน้า
  7. มีอย่างน้อย 1 คน แล้วจึงไปนับที่นั่ง (SEATS_EXCEEDED, 409)

การแก้ไขและยกเลิกใช้ CanModify() ตัวเดียวกันทั้งตอนตัดสินจริงและตอนบอกหน้าเว็บว่ากดปุ่มได้ไหม ทำได้ถึงเวลา เวลาเริ่ม − cancel_lead_minutes ของร้าน และตอนแก้ไขจะไม่นับที่นั่งเดิมของตัวเองซ้ำ (excludeID)

7ความปลอดภัย

Token ไม่อยู่ใน JavaScript

JWT ของ Go อยู่ใน cookie ของ NextAuth ที่เข้ารหัสและเป็น httpOnly ถึงหน้าเว็บโดน XSS ก็ขโมย token ออกไปไม่ได้

web/auth.ts

Logout ยกเลิก token ได้จริง

token มีค่า ver ฝังอยู่ และทุกคำขอจะเทียบกับ users.token_version ใน DB ถ้าลบ user ทิ้งหรือ logout ไปแล้ว token จะใช้ไม่ได้ทันที

middleware/auth.go

JWT แบบเข้มงวด

รับเฉพาะ HS256 (กัน alg: none) และบังคับว่าต้องมีวันหมดอายุ กุญแจต้องยาว ≥ 32 ตัวอักษร ถ้าไม่ได้ตั้งไว้ ระบบจะสุ่มเก็บลง app_secrets ใน repo จึงไม่มีค่าลับ

cmd/api/main.go

กัน CSRF

คำขอที่ไม่ใช่ GET ต้องมี Sec-Fetch-Site: same-origin ซึ่งเบราว์เซอร์ใส่ให้เองและเว็บอื่นปลอมไม่ได้ ซ้อนกับ cookie แบบ SameSite=Lax อีกชั้น

app/api/v1/[...path]/route.ts

Rate limit

login ผิด: 10 ครั้ง / 15 นาที ต่ออีเมล · สมัคร: 10 ครั้ง / ชม. ต่อ IP และ 100 ครั้ง / ชม. รวมทั้งระบบ · เขียนข้อมูล: 60 ครั้ง / นาที ต่อคน · อัปโหลด: 30 ครั้ง / 10 นาที

handlers/limits.go

ลดช่องทางโจมตี

ใส่รหัสผิดกับใส่อีเมลที่ไม่มีในระบบได้ข้อความตอบกลับเหมือนกันทุกตัวอักษร · password_hash ไม่ถูกส่งออกใน JSON · API และ DB เปิดให้เฉพาะเครื่องนี้ · callbackUrl รับเฉพาะ path ในเว็บเรา
